# Horizon memory semantics: options and timeboxed capability proof

HZ-MEMORY-001 investigates the defects recorded under HZ-PORT-002. This is an authored analysis; no implementation or hardware acceptance is implied.

The current backend groups committed ranges into code-memory objects. The pinned Eden image (`sha256:68d0f0847e3ff18f84eedb227b38b5e1a977c036dc202ee6b01debf72762fecb`) source `core/hle/kernel/k_code_memory.cpp` checks that Map/Unmap/MapToOwner/UnmapFromOwner sizes equal the entire object's page count. That contradicts treating an arbitrary subrange decommit as a direct unmap of an existing large object. Its object initialization also clears backing bytes to0xFF; the runtime's post-map zero is therefore necessary in the tested implementation. These are source observations about this emulator, not hardware measurements.

A two-page synthetic NRO was built/run once in the existing pinned toolchain/runner to measure partial owner-unmap, partial permission removal, whole unmap/remap and preservation of written bytes. It never frees backing while an owner mapping remains live. The raw commands/results remain private under `game/build/horizon-memory/`. The probe result describes capabilities only; it does not establish corrected Win32 wrappers.

Executed result (Eden only): build/run exit0; partial owner-unmap returned `0xCA01`, partial permission removal returned `0xD401`, and both pages remained CodeWritable with RW permissions. Whole unmap/remap succeeded and both written page patterns were preserved. Cleanup succeeded. NRO SHA-256: `a44c429e15c022a4e0b1ccbf8032d4930558a351c3ad25d3a703d2d65798a6d9`. This rules out direct partial unmap/protection in this runner. Hardware remains UNVERIFIED.

| Option | Result/constraint | Decision |
|---|---|---|
| Zero bytes and retain current mapping | Recommit zeroing can be imitated, but decommitted pages remain readable/writable and counted as mapped | Insufficient for full semantics; cannot close HZ-MEMORY-001 |
| Protect subpages with no access, if supported | May give access semantics with metadata, but retains backing storage; actual service capability must be measured | Investigate in this bounded probe, no inferred support |
| One code object per page | Permits page-granular unmap but the current512-entry registry covers only2MiB; guest backing is much larger | Reject this unbounded handle/registry expansion as the first fix |
| Split/rebuild affected whole objects transactionally | Prepare retained fragments and byte shadows before unmapping; map/copy fragments after unmap; preserve original object for rollback | Selected for implementation after the bounded probe; transient memory/resource cost and rollback must be proved |
| Different mapping primitive | Could avoid code-object granularity but must support the chosen guest address window and partial unmaps | No capability claim; requires a separate timeboxed proof before implementation |

For split/rebuild, failed preparation leaves existing mappings intact. A failure after unmapping must remove only newly mapped fragments and restore the retained original handle without rerunning guest code. Never close/free a still-mapped backing. If kernel failure prevents restoring a consistent map, stop rather than return success into corrupted guest memory. A mocked-service test must exercise each failure boundary; an actual Horizon NRO must verify unmapping and preservation. Peak memory and resource exhaustion remain explicit limits, not silent shortcuts.

Independent ownership fixes also require: checked page/overflow arithmetic; tracked fixed-address reservations; release of every committed run inside a released reservation; rollback of new partial commits/reservations; a mapping-owned backing lifetime across unmap/remap; active-view references when a mapping handle closes before unmap; and locking both the second-view check and publication. A remap test must verify previous contents, not merely a non-null pointer. These requirements must not be weakened by the capability result.

The selected implementation will prepare retained fragments and byte shadows before the first unmap. For a64MiB object with a one-page hole, this requests approximately128MiB of temporary allocation in addition to the original64MiB backing; tests must report requested allocation peak separately from physical memory. Fixed registry capacity will be checked before mutation.
